# 实例操作并发优化

## 目标与边界

减少实例占用造成的重复点击，让互不影响的准备工作重叠执行。继续保持每实例一个写任务、每游戏安装一个维护任务和节点 SteamCMD 并发上限；取消待确认及终态待投影仍持有写锁。跨实例普通任务已经并行，不增加全局串行队列。

## 第一阶段：已实现

1. 插件压缩包预检不再占 Control 的实例写锁，与 Agent 已有的只读分类一致。下载、解包和计划生成可与实例写任务并行；每实例最多一个活动预检，避免重复点击产生大量并行解包。预检只是当时的诊断，正式安装继续在写锁内重新校验文件、归属和接管条件。
2. 批量启用、停用、删除在收到明确的实例占用拒绝后等待当前条目，不再把整批快速标为失败。等待以 750 毫秒开始、指数退避到 3 秒，每项最多等待 10 分钟；收到任务 ID 后仍等待该任务终态及写锁释放，才提交下一项。
3. 409 保留 `conflict` 错误码，实例占用额外返回 `reason=instance_busy` 和 `blocking_job_id`。前端仅重试这种明确未创建任务的拒绝，同一条目复用原幂等键及原请求内容。普通 409、权限拒绝、网络断开和服务端错误不自动重试。每次重试都重新经过服务端权限、状态、依赖检查。
4. 停止或离开页面后不再提交剩余条目；已经提交的任务继续由任务中心管理。等待发生在当前页面，不是持久服务端队列；刷新不恢复未提交操作。
5. 新增前向迁移 019，保留任务 ID、外键、幂等记录及写锁状态语义。两个锁分类字段仍为生成列，写锁继续使用唯一部分索引；使用虚拟生成列避免重建被多张业务表引用的 jobs 表。旧迁移不修改。

模组扫描会把磁盘发现结果写入 Control 包清单。现有防陈旧结果逻辑只覆盖部分并发变更；本次保留其 Control 写锁，避免删除、停用、恢复与延迟扫描结果交错导致记录复活。

## 后续实施阶段：并行准备、串行提交

此阶段尚未实现，不能通过简单移除现有锁完成。

- 拆分固定的包准备和安装任务，通过新能力协商只发给支持的 Agent。准备阶段只写 Agent 自有 staging，不取得实例写锁；共享节点下载槽、磁盘配额、解包数量及展开大小限制。
- 准备结果返回绑定节点、实例、包摘要及有效期的不透明句柄，不能返回或接受任意主机路径。持久记录准备结果，重启、取消、到期后回收 staging；原始来源和上传定位符继续按秘密处理。
- 安装阶段取得现有实例写锁，重新核对准备产物 SHA-256、大小、实例状态、包依赖、目标路径及接管确认，再执行既有 no-follow 原子提交和回滚。开始等待前的文件状态不能作为提交时的依据。
- 需要服务端持久排队时，将等待意图与占锁执行任务分开建模。派发前重新授权并校验状态，保留既有状态机和幂等行为；不能仅从唯一索引中删除 queued，否则现有配置投影及生命周期状态会提前变化。
- 扫描若要并行，需要实例变更代际或覆盖所有相关写任务的结果失效机制，保证旧扫描不会重建刚删除、改名或回滚的包记录。

验收比较相同节点、相同包集合的批量完成时间、占锁时间及冲突次数；覆盖断线重连、重复提交、停止等待、权限撤销、Agent 重启、准备过期、磁盘不足、安装回滚和扫描交错。吞吐改善取决于网络、磁盘和解包开销，不预设提速倍数。
